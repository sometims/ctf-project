# WP · qsnctf 40555 — SSRF 绕过"只拦回环"黑名单，打进内网应用拿 flag

> 题目：`http://challenge.qsnctf.com:40555/`
> 标题：内部威胁情报监控平台 - URL分析器
> 类型：**SSRF（Server-Side Request Forgery，服务端请求伪造）**
> 环境：**gunicorn + Flask**（响应头 `Server: gunicorn`，不是 PHP）
> Flag：`flag{aeab080a8087419db1b0618981912d86}`
> （页面显示成 `FLAG{flag{aeab080a8087419db1b0618981912d86}}`，外层 `FLAG{}` 是前端模板 artifact，真实提交用内层 `flag{...}`）

---

## 0. 一句话思路

URL 分析器会把你输入的 URL 让服务器去请求并回显结果 → 经典 SSRF。它拦了 `127.0.0.1`/`localhost`/`0.0.0.0` 等回环地址，但**没拦 Docker 网桥网关 `172.17.0.1`**。而 gunicorn 监听 `0.0.0.0:40555`，用 `172.17.0.1:40555` 就能访问到服务器自身、绕过回环黑名单；接着在内网发现第二个容器 `172.17.0.2:80`（"安全贷款顾问"应用），其首页直接把 flag 写死在 HTML 里。

---

## 1. 初步侦察：这是 Flask 的 SSRF

响应头 `Server: gunicorn` 说明是 Python/Flask，和前几题的 PHP 完全不同。

首页是一个表单（`POST /`，字段 `url_to_analyze`），标注"URL分析器 / 威胁情报"。

提交 `url_to_analyze=http://example.com` 后，页面回显了：
- 状态码 `200`
- 响应头
- 响应体（Example Domain 的完整 HTML）

→ **服务器真的替你去请求了 URL 并把结果喂回来**，这就是 SSRF 的黄金入口。

## 2. 确认注入点

`view` 类 SSRF 不需要单引号，关键看"服务器是否按你的 URL 发请求"。example.com 成功回显即可确认。

## 3. 测绘黑名单（最重要的一步，决定打法）

拿 `http://127.0.0.1/`、`file:///etc/passwd`、`dict://`、`gopher://` 一试，全部**瞬间失败（0.1~0.2s 秒拒）**，且页面 `analysis-result` 区块直接消失（静默返回空表单）。

逐类测试后，按"秒拒 vs 超时"二分：

| 输入 | 结果 | 解读 |
|---|---|---|
| `http://127.0.0.1/`、`localhost`、`0.0.0.0`、各种 IP 进制、回环族 127.0.0.2/3、全角句号 `127｡0｡0｡1`、`@` 混淆 | **秒拒** | 被黑名单拦 |
| `file://` / `dict://` / `gopher://` | **秒拒** | 非常规协议被拦 |
| `http://1.1.1.1/` | OK（301，且被回显） | 公网 IP 放行，**且后端跟随 301 重定向** |
| `http://example.com` | OK | 公网域名放行 |
| `http://172.16.0.1/`、`10.0.0.1/`、`192.168.1.1/`、`169.254.169.254/` | **超时（4.2s，非秒拒）** | **未被拦，只是连不上（无服务）** |

**核心结论**：黑名单**只拦回环地址（127.0.0.0/8）和 0.0.0.0**，对其他私有网段（10/172.16-31/192.168）根本没拦——它们之所以"失败"只是因为那个 IP 上没有监听服务（连接超时）。

## 4. 常规绕过尝试（全失败，记录避坑）

因为黑名单是"解析后判定 IP 是否回环"，以下全部失效：
- IP 进制变形：`2130706433`(十进制)、`0x7f000001`、`0177.0.0.1`、`127.1`、回环族 `127.0.0.2/3` → 解析后仍是回环，被拦
- 域名解析到内网：`localtest.me`、`127.0.0.1.nip.io` → 解析成 127.0.0.1，被拦
- `@` 混淆（`http://example.com@127.0.0.1`）、`#` 片段 → 后端用标准 `urlparse().hostname` 取 host，检查与执行一致，被拦
- 全角句号 `127｡0｡0｡1`（U+FF0E） → 解析失败或被当回环，被拦
- 302 跟随：后端 `allow_redirects=True`（1.1.1.1 的 301 被回显证实），但手边没有能 302 到内网的公网可控源（httpbin 在题目网络里不可达），此路不通
- 直连外网路径：`/flag.txt` `/app.py` `/.git/HEAD` 等全是 404，flag 不在公网直连能拿的地方

## 5. 突破口：用 Docker 网关 `172.17.0.1` 代替回环

黑名单只拦 `127.0.0.1`，而 **`172.17.0.1` 是 Docker 默认网桥 docker0 的网关地址（宿主机在容器网络里的 IP）**，明显不在 127/8 内 → **不会被拦**。

又因为 gunicorn 监听的是 `0.0.0.0:40555`（否则外网根本打不进来），从容器内访问 `172.17.0.1:40555` 会经过 Docker 端口映射回到容器自身的 Flask。

于是：
```
POST /  url_to_analyze=http://172.17.0.1:40555/
→ 返回 200 + Flask 首页（成功绕过回环黑名单，访问到自身应用！）
```
（注意 `172.17.0.2/0.3/0.10` 是"秒拒"而非超时，说明它们是真实存在的其他容器，只是 :40555 没服务被 RST；而 `172.17.0.1` 网关有端口映射，所以成功。）

## 6. 内网横向：找到泄漏 flag 的第二个容器

能访问自身 Flask 后，枚举它的路由（`/flag`、`/secret`、`/admin`、`/source`…）全 404——flag 不在 Flask 的 HTTP 路由里。

转而扫宿主机 `172.17.0.1` 的其它端口（80/443/8080/3306/6379…）→ 只有 40555 有服务。

再扫**另一个容器 `172.17.0.2`** 的端口，发现 **`172.17.0.2:80` 开放 HTTP**！访问它：

```
POST /  url_to_analyze=http://172.17.0.2:80/
→ 返回 "安全贷款顾问" 应用首页
→ 其中 "FLAG状态" 区块直接写死：
   <code id="current-flag">FLAG{flag{aeab080a8087419db1b0618981912d86}}</code>
```

这就是 flag。（该应用是个 AI 聊天应用，有 `/chat` 端点和 basic/permission/context 三个场景，首页服务端渲染时就把 flag 注入进去了；`main.js` 里 `currentFlag.textContent = newFlag` 证实显示值直接来自后端。）

## 7. 完整利用链（payload 顺序）

```
# ① 确认 SSRF
url_to_analyze=http://example.com

# ② 绕过回环黑名单，访问自身 Flask（拿到分析器自身的响应，证明通道通）
url_to_analyze=http://172.17.0.1:40555/

# ③ 横向到内网第二个容器，直接读到泄漏的 flag
url_to_analyze=http://172.17.0.2:80/
```

在 ③ 的响应体里搜索 `flag{` 即得：
**`flag{aeab080a8087419db1b0618981912d86}`**

## 8. 这题教会你的 4 个关键知识点

1. **SSRF 判定标准**：提交外网 URL 后页面回显"状态码+响应头+响应体"，就基本坐实服务端会替你发请求。
2. **"秒拒 vs 超时"二分法**：SSRF 题后端请求失败时有两种表现——
   - **秒拒（<1s）** = 请求**根本没发出**（被 WAF/黑名单拦）；
   - **超时（~4s）** = 请求**真发出去了，但目标连不上**（IP 没被拦，只是无服务）。
   用这个二分能快速反推黑名单到底拦了什么。
3. **"只拦 127.0.0.1"是最常见的疏漏**：很多 SSRF 防护只 `is_loopback` 检查（拦 127/8 + 0.0.0.0），却忘了 Docker 网关 `172.17.0.1`、其它私有段。用网桥网关 IP 代替回环地址，就能访问"服务器自己"绕过限制。
4. **打通 SSRF 后要做内网横向**：先访问自身确认通道，再扫同网段其它 IP/端口，常见 flag 藏在"另一个内部服务"里（本题是 172.17.0.2:80 的应用把 flag 写死在首页）。

## 9. 避坑提醒

- 别像我一开始那样闷头试 IP 进制/`@` 绕过——**先系统测绘黑名单**（秒拒 vs 超时），否则会在死胡同里打转（参考 40554 那题的教训）。
- 回显为空 ≠ 没漏洞：本题请求失败是"静默空表单"（无 `analysis-result` 区块），要用"分析报告"字样判定是否成功，别被 CSS 类名 `.analysis-result` 误导。
- flag 显示成 `FLAG{flag{...}}` 双花括号时，按平台惯例取内层 `flag{...}` 提交（qsnctf 全站统一 `flag{...}` 格式）。
